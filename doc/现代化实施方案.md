# Dev-Cpp-Modern 现代化改造实施方案报告



## 1. 现状评估与改造目标


1. 编译器与平台限制：仍基于 Delphi 10.2 Tokyo 构建 32位程序，受限于虚拟内存地址空间，易因大型工程导致 OOM；
2. 上帝窗体与紧耦合：main.pas与 main.dfm聚合了大量界面控件与业务逻辑；全工程广泛存在 uses main及直接访问 MainForm.* 的强依赖，循环依赖严重，无法单独做单元测试；
3. 语言分析与调试器协议落后：内置的 ClassBrowsing 基于老旧的类 ctags 机制，无法准确解析 C++17/20/23 的模板元编程与 Concepts 特性；调试子系统仍基于已淘汰的 GDB Annotate 协议，极易在较新 GDB 版本中崩溃或解析失真；
4. 编译工具链老化：默认绑定的 TDM-GCC 9.2 过旧，缺乏对现代 MSVCRT/UCRT、C++20/C++23 标准库及 UTF-8 编码路径的原生完备支持；
5. 基础设施与工程质量薄弱：仅有 496 行的 Tests.pas 手动冒烟测试，无自动化 CI/CD 流水线，依赖项全量 Vendored 且未模块化；

### 1.2 改造目标（To-Be架构指标）
* 平台与运行时：升级至 Delphi 12+，提供 原生 Win64 目标架构；
* 解耦与架构：实现 main.pas UI 与业务逻辑剥离，引入 MVP / 观察者模式与服务定位器，消除反向 uses main；
* 智能提示与语言服务：保留 SynEdit 编辑器视图，逐步过渡并引入 LSP (Language Server Protocol) 对接 clangd，提供现代级补全、诊断与重命名；
* 调试引擎升级：重写 Debugger.pas / DebugReader.pas，全面转向 GDB MI (Machine Interface) 协议；
* 工具链与分发：默认集成现代 MinGW-w64 (UCRT + GCC 14+) 或 LLVM-MinGW，建立 GitHub Actions 全自动化 CI/CD 与打包分发。


## 2. 关键实施专题方案



### 专题一：Delphi 工具链升级与 Win64 原生移植

#### 实施要点
1. 项目工程升级：将 devcpp.dproj 升级到 Delphi 12 Athens 标准；添加 Win64 平台构建目标，配置独立的输出目录。
2. 依赖库清理与 64位兼容适配：FastMM5 调整配置以支持 64位高并发内存管理；SynEdit 升级至支持 64位、Per-Monitor DPI v2 及支持 DirectWrite 渲染的最新分支；VCL-Styles-Utils / Abbrevia 排查内联汇编及涉及 32位指针算术的代码，确保指针安全。
3. 编码规范与类型安全：排查 Windows API 交互（如 SetWindowLongPtr、GetWindowLongPtr、GWLP_USERDATA 的类型定义错误），杜绝 Cardinal/Integer 强转指针的踩坑隐患。


### 专题二：主窗体解耦与上帝类重构

#### 实施要点（三步拆解法）
1. 第一步：建立服务定位器与事件总线（消除反向 uses main）
   建立 Core.Services.pas 与 Core.Events.pas：定义 IProjectService、ICompilerService、IDebuggerService 等抽象接口；将其他单元中 MainForm.SomeMethod 的直接调用改造为接口调用或发布/订阅模式。
2. 第二步：剥离业务逻辑至独立 Controller/Manager
   从 main.pas 中剥离出以下子系统，仅将界面控件交互保留在 TMainForm：TProjectController、TEditorController、TToolchainController。
3. 第三步：精简 main.dfm
   逐步将各工具栏、停靠面板封装为独立的 TFrame，大幅降低主窗体 DFM 复杂度，避免多人协作冲突。


### 专题三：调试引擎与编译器子系统现代化

#### 实施要点
1. 调试器全面迁移至 GDB MI 协议：废除依赖控制台非结构化输出的 GDB Annotate 解析逻辑；重构 DebugReader.pas 与 Debugger.pas，编写状态机驱动的 GDB/MI异步解析器；预留接口抽象 IDebugEngine，为未来平滑引入 DAP 对接 LLDB 奠定基础。
2. 现代工具链支持与配置系统重构：重构 devCFG.pas：引入基于 JSON 格式的动态 Toolchain Profile存储，替代原单一硬编码的注册表/INI 项；默认预装支持 MinGW-w64 (UCRT runtime)，全面兼容 C++17/20/23/26 编译参数与 UTF-8 源码/控制台输出；改进 Compiler.pas 中的命令行拼接与错误解析正则。


### 专题四：现代代码感知升级（LSP 与 Clangd 引入）
Dev-C++ 当前的代码补全和类浏览在现代 C++ 语法下表现欠佳。建议采用双轨演进策略：1. 阶段性过渡：短期内对现存 SynEdit 内部语法高亮进行更新，支持 C++20/23 关键字与属性语法。2. 长期演化架构（LSP Client集成）：编写无头 LSP 客户端单元，通过匿名管道与后台运行的 clangd.exe 进行 JSON-RPC 通信；对接核心 LSP 方法：textDocument/completion、textDocument/publishDiagnostics、textDocument/definition、textDocument/rename。替换原先低效易崩的后台 ctags 扫描机制。


### 专题五：工程质量、依赖治理与自动化 CI/CD
1. 构建与测试自动化：重构 Tests.pas，引入 DUnitX 框架，将编译参数组装、INI/JSON 序列化、GDB MI 解析等无 UI 逻辑纳入单元测试覆盖；编写 GitHub Actions 流水线。2. 依赖项模块化：对 Vendored 目录进行版本封箱，记录 Upstream Commit，建立更新规范；删除未使用的历史代码分支。3. 打包分发现代化：升级 NSIS 脚本，统一生成 64位安装包；支持便携版；接入 WinGet / Scoop 社区源自动提交工作流。

## 4. 风险控制与应急预案

1. 依赖库不兼容 Win64风险：若个别老旧 Vendored 控件移植 64位成本过高，可考虑优先采用现代 Delphi 原生体系或成熟开源库替代。

2. main.pas重构引发回归 Bug：实行小步提交 关键链路冒烟测试锁定，重构前针对核心功能建立自动化冒烟测试。

3. LSP内存开销风险：针对低配机器保持 LSP 可配置选项 默认启用 同时保留轻量级内建自动完成 允许用户在极轻量模式与智能感知模式间切换。
